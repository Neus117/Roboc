## 刚刚解决的关键问题：注册表写不进去

### 症状

程序无法写入 `HKEY_CURRENT_USER` 下的任何位置，包括最普通的
`HKCU\Software\RobocProbe`。而同一台机器上，PowerShell 用**同一个 .NET API**
写入完全成功。

### 根因

**那个 exe 文件本身带着 `Low` 强制完整性标签。**

- Windows 规则：**Low 完整性级别的进程不能写 `HKCU\Software`**，这不是权限问题
- 标签从**文件**继承，所以任何从该文件启动的进程都被压到 Low
- 连它启动的 `reg.exe` 也是 Low，因此同样被拒
- 而 PowerShell 启动的 `reg.exe` 是 Medium，所以能成功

标签来自构建过程：**Low 完整性进程创建的文件会获得 Low 标签**，而我这边的开发
shell 是沙箱化、以 Low 运行的。于是编译器写出的 exe 带上了 Low 标签，这个 exe
又把从它启动的一切拖到 Low——**在任何机器上都是如此**，包括 shell 处于 Medium
的机器。这就是为什么两个毫不相干的环境出现了完全相同的故障：它们只共享那个文件。

### 排查链

| 观察到的 | 排除掉的可能 |
|---|---|
| 火绒日志无拦截记录 | 安全软件 |
| 非裁剪、非单文件的构建同样失败 | 裁剪 / 单文件打包 |
| 去掉清单里的 `activeCodePage` 无变化 | 应用程序清单 |
| PowerShell 用**同一个 .NET API** 写入成功 | 权限问题、API 误用 |
| `reg.exe` 由 PowerShell 启动成功、由本程序启动失败 | 工具本身 |
| **`diagnose` 报 `Low (4096)`，PowerShell 是 `Medium (8192)`** | 以上全部 |

最后一行就是答案。整条链上只有"进程自己的完整性级别"是从程序内部看不见的。

### 修复

```
icacls <exe> /setintegritylevel Medium
```

**每次发布之后都必须执行这一步。** 构建本身会重新制造这个问题，因为编译器运行在
Low。没经过这一步的产物装不上任何东西，只会报一句"拒绝访问"。

修复后确认：`diagnose` 报 `Medium (8192)` 与 `5/5 个位置可写`，
`install` 一次注册全部 13 个键，无需任何绕行。

## 已知缺口

按重要性排序。

### 1. 菜单位置未调整

你要求把 Roboc 放在系统"粘贴"**上面**。这件事**我做不到精确控制**：
静态菜单项在系统项（查看/排序/刷新/粘贴/新建）之后，唯一的杠杆是 `Position`
值，而它只支持 `Top` / `Bottom` 两档。

用 `Top` 会放到最顶上（在"查看"之上）。**等你确认功能都正常后我再加**，你先看
实际效果决定要不要退回去。

### 2. 回收空间的图形界面未做

目前是命令行：`reclaim` 列出项目、大小、原路径；`reclaim --empty --yes` 清空。
你要的是界面，排在下一步。

### 3. "能否在盘根建目录"未验证

回收站默认建在 `<盘符>:\Roboc_bin`，而我这个环境**不允许本程序在
workspace 之外建目录**。所以我加了 `ROBOC_BIN_ROOT` 环境变量把回收站重定向
到 workspace 内，用它验证了**除盘根权限之外的全部逻辑**。

正常情况下普通用户在数据盘根建目录是允许的，但**这一点需要你在真机上确认**。
那个环境变量本身也是有用的功能（想把回收站集中放一处的用户），已作为公开开关保留。

### 4. 重解析点（junction / 符号链接）重建不工作

代码已实现（`Fs/ReparsePoints.cs`），读取正常（tag `0xA0000003`、308 字节缓冲区
与 `fsutil` 一致），但 `FSCTL_SET_REPARSE_POINT` 返回 `ERROR_INVALID_FUNCTION`。

同一个目标目录、同一个卷上，`New-Item -ItemType Junction` 和 `mklink /J` 都能
成功，只有本程序的调用不行。**这个现象现在有了新的解释**——很可能同样是完整性
级别问题（Low IL 对某些文件系统操作有限制）。**修好标签之后值得重测一次。**

当前的失败行为是安全且诚实的：错误信息带 tag 和缓冲区大小，而且**失败时创建的
空目录会被清理掉**（一个名字对但是空壳的目录比"跳过"更糟，它看起来像成功了）。

每个链接被复制成独立文件，所以产出物正确但比源大。`FILE_ID_INFO` 的管道已经就位。

## 测量纪律：这台机器的存储会被自己的负载拖垮

一次对比测试做了 27 次 20,000 文件的递归删除，把系统卷从 900 MB/s 压到 1 MB/s，
**只有重启才能恢复**。

`bench/run-bench.ps1` 现在内置了防护：

- **每轮之前跑体积探针**，用的正是会拖垮硬盘的那个操作（大量小文件创建）。
  健康约 3900 文件/秒，约 2000 表示半速；低于 3000 标记 SUSPECT，
  轮间漂移超过 3 倍标记 UNRELIABLE
- **轮次交错**，任何漂移均等地落在所有方案上
- **只在结尾清理一次**，绝不在轮次之间清理
- 生成器的 stderr 会被显示出来；测量前用真实二进制探测 scratch 是否可写

**测量脚本要写进 `run-bench.ps1`，不要再写临时脚本。** 连续三个临时脚本都产生过
看似可信的垃圾数据：`$Args` 是 PowerShell 的自动变量，用作参数名会静默失效；
一个多余的 `\r` 让行过滤器失效；`ToString("D3")` 抛异常导致语料根本没生成，
于是两个工具都"复制"了零个文件。

## 已定的设计决策与理由

### 发布策略是分级的，不是统一的

小于 `LargeFileThreshold` **且目标不存在**的文件直接写最终路径；其余走临时文件
+ 原子改名。

测量驱动了这个决定：创建目标 + 改名占了小文件复制的 **89%**，而真正的数据传输
只占 **2.8%**——因为暂存比 `CopyFileEx` 多一次目录项更新。分级回收了 **1.6–1.9 倍**，
正好是"输给 robocopy"与"打平"之间的差距。

**覆盖场景仍然走暂存**，因为直写会立刻截断原文件，中途失败会连原文件一起毁掉。

### 删除需要 `--yes`，默认暂存

十秒的撤销窗口曾是默认。**现在被回收站取代**——回收站是持久的、可浏览的、
可通过资源管理器手动还原的，比时间窗口更有用。

### 用 `asInvoker`，不用 `requireAdministrator`

无条件提权会让每次菜单调用都弹 UAC，让 Administrators 成为所有新建文件的所有者，
并隐藏映射的网络驱动器。提权是按需、按任务的。

### 独立回收站，不混用系统的

混进系统回收站意味着混进它的账本、它的容量统计、它的每用户配额和它的"清空"
语义。独立回收站让这些都成为本程序自己的决定，同时**完全不碰系统的回收站**。

命名 `<盘符>:\Roboc_bin\`，内部**镜像原路径**（去掉盘符冒号）：

```
D:\Coding\workspace\foo.txt
  → D:\Roboc_bin\D\Coding\workspace\foo.txt
```

好处有三个：**一眼看懂**、**资源管理器可直接浏览和手动拖回**、
**不需要任何索引文件**（还原目标可从存储路径直接推导，也就不存在索引与文件
不同步的问题）。

镜像结构本身有歧义（`回收站\D\a\b\` 里的 `b` 既可能是被回收的目录，也可能只是
路径脚手架），解法是**目录型回收项内含一个 `Roboc.回收信息.txt` 标记文件**，
记录原位置和回收时间。文件型回收项不需要标记——脚手架只可能是目录。

同卷回收是**一次改名**，所以回收一个百万文件的目录和回收一个文件一样快。

### 日志刷新是周期性的，而且这不只是"为了快"

丢失一条 `Done` 记录最多重传一个文件；丢失一条 `Checkpoint` 记录只可能把续传点
**向前回退**，因为复制器是先 `FlushFileBuffers` 数据再上报偏移。
**所以丢日志只会造成重复劳动，永远不会产出损坏数据。**

## 待处理清单

按优先级排列，更新于右键菜单功能打通之后。

### 1. 回收空间的图形界面（未做）

目前 `回收空间` 的行为是：**打开回收站目录** + 弹窗报告项目总数与占用空间。
这满足了"能看到、能进去清理"，但**你要的正式界面还没做**——一个列出项目、
大小、原路径，并能勾选清空的窗口。

### 2. 网络标记（MOTW）安全警告 —— 暂时搁置，原因未明

**症状**：展开右键菜单时弹出"Windows 安全中心：打开这些文件可能会对你的计算机有害"。

**已知**：
- 检查时 `12 / 394` 个文件带 `Zone.Identifier`（`ZoneId=3`），目录 0 个
- `Unblock-File` 清除后警告消失
- **但这些文件是用户手动创建文本文件后复制改名得到的**，理论上不该有网络标记

**未解**：那 12 个文件的网络标记从何而来。记事本或资源管理器的复制操作
不应写入 `Zone.Identifier`。可能与其他工具、或与文件曾经所在的位置有关。

**处理方式**：暂不深究。再次出现时先跑这段定位具体是哪些文件：

```powershell
$d = "D:\Coding\DeepSeek Harness\workspace\Roboc\manual test"
Get-ChildItem -LiteralPath $d -Recurse -File -Force -ErrorAction SilentlyContinue | ForEach-Object {
    $s = Get-Item -LiteralPath $_.FullName -Stream * -ErrorAction SilentlyContinue
    if ($s | Where-Object { $_.Stream -eq 'Zone.Identifier' }) { $_.FullName }
}
```

**需要区分的是**：这是 Windows 对带标记文件的正常保护行为，还是本程序触发的。
目前的证据指向前者——程序不写 `Zone.Identifier`，复制出的文件也不带该标记。

### 3. 重解析点（junction / 符号链接）重建不工作

代码已实现（`Fs/ReparsePoints.cs`），读取正常，但 `FSCTL_SET_REPARSE_POINT`
返回 `ERROR_INVALID_FUNCTION`。

**值得重测**：当时的失败很可能是 exe 的 Low 完整性标签所致，而那个问题已经修复
（见上文）。当前失败行为是安全的：错误信息带 tag 和缓冲区大小，失败时创建的
空目录会被清理。

### 4. 便携版不再严格单文件

菜单图标必须与 exe 一起发布（静态动词只能指向文件路径，无法寻址 exe 内部的
多个图标资源），因此 `artifacts\portable\` 现在是一个目录：

```
Roboc.exe          11.4 MB
assets\icons\*.ico      5 × 432 KB ≈ 2.2 MB
```

图标缺失时程序会退回使用 exe 自身的图标，菜单不会失去图标。

### 5. 硬链接不重建 / 备用数据流（ADS）不复制

硬链接被复制成独立文件（产出物正确但更大）；ADS 完全丢失。

### 6. 大文件中途续传只有单元测试

日志的检查点往返与截断容忍已在 `--selftest` 中验证，文件级续传也端到端验证过，
但**还没有一次是在大型文件复制过程中真正打断**并确认从记录的偏移继续。
