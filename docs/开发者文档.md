# 一、项目概览

**一个便携的单文件可执行程序**，深度集成资源管理器右键菜单，用性能优先的手段完成复制、粘贴、删除、回收。

| | |
|---|---|
| 平台 | Windows 11，.NET 10 |
| 语言 | C#，手写 Win32 P/Invoke，**无 MSVC、无 NativeAOT、无 COM 外壳扩展** |
| 产物 | `artifacts/portable/Roboc.exe`，**12.5 MB 单文件** |
| 代码 | 57 个 `.cs`，20,388 行（Core 11,382 / App 9,006），不含 `bin`、`obj` 与 `tools\Roboc.CorpusGen` |
| 自检 | **25 项**，`--selftest` |
| 测试机 | i7-12800HX，31.7 GB RAM，2560×1600 @ 175%（DPI 168） |

**开发机上没有 MSVC**——这排除了 NativeAOT、原生 DLL 与 COM 外壳扩展，所有原生能力必须通过 P/Invoke 实现。

# 二、构建与发布

**唯一合法途径：**

```powershell
powershell -ExecutionPolicy Bypass -File build.ps1
```

流程：构建 → 发布 → 复制图标 → **`icacls /setintegritylevel Medium`** → `--selftest`

## 必须做的一步：完整性标签

**DSH 派生的进程运行在 Low 完整性级别**，而 Low IL 进程**无法写入 `HKCU\Software`**。构建产物因此会继承 Low 级别，导致所有注册表写入被拒。

`build.ps1` 已自动处理，**但有三件事必须知道**：

| 对象 | 为什么要打标签 |
|---|---|
| `Roboc.exe` | 写 `HKCU` 注册菜单项 |
| **`Roboc.CorpusGen.exe`** | **Low IL 进程无法写入普通目录**——不打标签会报 `Access to the path ... is denied`，**读起来像目录权限问题，实际是程序自身级别太低** |

**手动补救**（若发布被跳过）：

```powershell
icacls <exe> /setintegritylevel Medium
```

## `.ps1` 文件必须带 UTF-8 BOM

**PowerShell 5.1 对无 BOM 的 `.ps1` 按 GBK 解码**，中文变乱码，进而引发一串看起来像语法错误的报错（"缺少右 `}`"、"Try 语句缺少 Catch"）。

**这个坑在项目中踩过两次**，其中一次是编辑工具写回时丢失 BOM。

## 发布可能静默失败

`build.ps1` 删除产物目录时若被占用，会报 `Access is denied` 但**仍继续执行并打印"完成"**——**路径指向的是旧产物**。

**发之前先杀掉残留进程**：

```powershell
Get-Process Roboc -EA SilentlyContinue | Stop-Process -Force
```

## 图标的两套机制

**必须分清，因为约束不同：**

| | 程序图标 | 菜单图标 |
|---|---|---|
| **位置** | `src/Roboc.App/Roboc.ico`，**内嵌进 exe** | `assets/icons/*.ico`，**外部文件** |
| **用途** | exe 在资源管理器里的样子、**窗口标题栏** | 右键菜单六项各自的样子 |
| **谁解析** | `AppIcon.Handle`（`LoadIconW` 读自身资源） | `ContextMenuInstaller.IconFor`（拼路径） |
| **为什么这样** | 窗口类能持有句柄，用二进制里已有的即可 | **静态注册表动词只能指向文件**，无法寻址 exe 内的某一个图标 |

**级联布局与平铺布局都必须走 `IconFor`。** 级联版曾经把每个菜单项的图标硬编码成 `quotedExe + ",0"`——于是六项显示同一个程序图标，而旁边六个专门画的图标一直没被用过。**平铺版一直是对的，只有默认启用的那个布局错了。**

**换程序图标**：把 `assets/icons/` 里想要的那个复制成 `src/Roboc.App/Roboc.ico` 重新构建即可。


## 几个关键设计

**选择集读取走 COM。** Explorer 的 `MultiSelectModel=Player` 在选中项超过约 15 个时改为只传被点击的那一项。**唯一可靠的方案是从前台 Explorer 窗口读 `Shell.Application` 的 `SelectedItems()`**，并用**被点击项的父目录**匹配窗口（`ShowsFolder`）——**绝不能用焦点匹配**，Win11 右键菜单是 XAML 弹窗，其 owner 链不通向文件夹窗口。

`AppliesTo` 是死路——试过四种表达式，全部导致菜单项整体消失。

**多进程去重。** 一次操作会派生多个进程（每个选中项一个）。第一个抢到锁的执行，**其余静默退出**。而锁在进程退出时释放，所以迟到的进程会**再次处理同一批**——为此加了"已处理指纹"标记（路径集合的 SHA256 + 时间戳，15 秒有效）。

# 四、设计决策与理由

**这一节记录"为什么不那样做"。** 每一条都对应一次实测或一次踩坑。

## 删除

| 决策 | 理由 |
|---|---|
| **删除默认进回收站**，`--direct` 才是永久 | |
| **`--yes` 是清空回收站的唯一途径** | 原先接受 `--gui-errors` 替代它，理由是"菜单路径会显示确认对话框"——**但菜单从不传 `--empty`，那个对话框不可达，这个豁免等于无确认清空的后门** |
| 三道防线：`GuardDriveRelative` / `GuardAgainstVolumeRoot` / `GuardAgainstSelf` | 见第六节的事后分析 |

## 复制

| 决策 | 理由 |
|---|---|
| 小于 `LargeFileThreshold`(2 MB) 且目标不存在 → **直接写** | 暂存+改名在快路径上是纯开销 |
| 否则 → 暂存 + `FileRenameInfoEx` POSIX 改名 | 目标路径永不被观察到半成品 |
| 大文件走 **overlapped 双缓冲** | |
| **`UseUnbufferedIo` 已删除** | 默认 `true` 却无人读取。无缓冲 I/O 要求偏移、长度、缓冲区地址全部扇区对齐，而**实测显示大文件复制已达 1034 MB/s、卷的持续写入上限是 967 MB/s——已经在设备极限上**，绕过它并不等待的缓存不可能有帮助 |
| **检查点间隔保持 32 MB** | 曾尝试提到 256 MB，**测量结果自相矛盾**（32MB:1.02s / 256MB:1.18s / 1GB:4.11s，且 `--no-resume` 比开着更慢），缓存淘汰主导了顺序测量。已回退 |

## 回收

| 决策 | 理由 |
|---|---|
| 每卷一个独立回收站，`<卷>:\Roboc_bin\` | 与系统回收站互不干扰 |
| **扁平布局**：`<bin>\<叶子名>` + 同名 `.txt` 边车 | |
| 原路径由 **边车 → 标记 → 镜像算术** 三级兜底 | |
| **同名不再回收**，拒绝并说明 | 否则取回时无法判断该还原哪一个 |
| 回收站内项目无法再次回收，**改为提示取回** | 静态动词的标签无法随选择变化，`AppliesTo` 又不通 |

## 视觉

| 决策 | 理由 |
|---|---|
| **一切尺寸以磅与逻辑像素声明** | 固定 `-12` 像素的字高在 175% 缩放下只有系统 UI 的 **57%** |
| **窗口创建前必须用 `GetDpiForSystem()`** | `GetDpiForWindow(0)` 在窗口存在前**恒返回 96** |
| **不用 Mica 背景** | 它的前提是窗口不自绘背景；自绘窗口启用只会让 DWM 合成的边缘混成污渍 |
| **不用 `WS_THICKFRAME`** | 可调边框会让合成边缘与自绘内容对不齐 |
| 对话框**全部自绘**，不用 `MessageBoxW` | `MessageBox` 的字体、配色、圆角**全部无法设置**，这正是过去"两个弹窗像两个程序"的原因 |
| **标题栏涂成比卡片深一档的灰** | 顶栏由 DWM 用 Mica 绘制，会随壁纸着色；与自绘的中性灰卡片拼在同一扇窗上就成了两种颜色（见第五节 E 类） |

### 主图标在深色主题下的实测数据（已评估，决定不改）

**测于 2026-10-13，Windows 11 build 26300，深色任务栏底色 `#202020`（亮度 32）。**

`Roboc.ico` 的构成：

```
不透明区域 52%（其余透明）
  暗色像素 100%
  中间调     0%
  亮色像素   0%
```

**对深色任务栏的最大亮度差：**

| 图标 | 最大亮度差 | 判定 |
|---|---|---|
| **Roboc（主图标）** | **32** | **几乎不可见** |
| copy / paste | 45 | 偏弱 |
| delete | 63 | 清晰 |
| recycle_bin / settings | 82 | 清晰 |
| recycle | 105 | 清晰 |

**这是"纯黑线条 + 全透明背景"的必然结果。** 而主图标是唯一必须出现在**任务栏、Alt-Tab、通知区域**的图标——那些位置的背景由用户主题决定，与右键菜单（永远浅色）不同。

**作者已在实机深色主题下目视确认可用，并选择保留该设计。** 渲染脚本的对比度估算与真实观感存在差异，且这是设计意图的一部分。

**留档的理由**：这个结论以后会被重新"发现"。**再发现一次不等于需要再改一次**——除非作者改变主意，或收到"任务栏上看不见"的用户反馈。

**若将来要改**，代价最低的方案是给 R 加一个实心底色（沿用菜单图标的蓝）。**一次改动同时解决可见性与"主图标与六个菜单图标风格不统一"两个问题。**


## 参数与配置

| 决策 | 理由 |
|---|---|
| **接受一个参数却什么都不做，比拒绝它更糟** | 拒绝只花一秒钟，虚假的保证可能让人丢掉它本该保护的数据 |
| `--verify` **已实现**，默认关 | Windows 原生复制**不做任何校验**（`CopyFileEx` 无此选项），这是差异化能力 |
| `--ads` **已实现**，默认关 | 探测数据流要**每文件一次 `FindFirstStreamW`**，实测 19 µs（对照：读时间戳 16 µs），约 **3.8–7.4%** 吞吐 |

# 五、已修复的缺陷

**按性质分类。注意其中绝大多数属于同一族。**

## A. "代码正确但画面空白"（4 例）

| 缺陷 | 表象 |
|---|---|
| 网格线画在填充之前，被不透明填充盖住 | 该看见的没看见 |
| `DT_CALCRECT` 用于绘制（而非测量） | 有按钮没正文 |
| 缺 `WS_CLIPCHILDREN`，父窗口每帧刷掉子按钮 | 有句柄没按钮 |
| `Marshal.PtrToStructure<T>` 用于类 | 异常穿过 P/Invoke 回调边界，**进程静默退出、退出码 0** |

**只有截图能发现这一类。** 读代码看不出。

## B. "承诺与实现不符"（7 例）

| 声明 | 实际 |
|---|---|
| `CopyAlternateDataStreams = true` | 无人读取 |
| `VerifyChecksum` | 无人读取 |
| `--verify` | 接受参数，什么都不做 |
| `UseUnbufferedIo = true` | 无人读取（已删除） |

| **`--export-reg`** | **未注册进 `TakesValue`，存在至今** |

**前六次靠人眼审查发现，第七次由 `scripts/check-wiring.ps1` 自动发现。**

## C. "失败信息未抵达需要它的人"（4 例）

| 位置 | 表象 |
|---|---|
| `Walk` 把文件当目录枚举 | 该数的没数 |
| `OnItemWritten` 只对文件触发 | 该选的没选 |
| `Invoke-Timed` 丢弃 stderr | 该报错的说"耗时 0.2 秒" |
| `$Corpora` 参数覆盖 `$corpora` 数组 | 该跑测试的说"语料不存在" |

**第四例的成因**：PowerShell 变量名不区分大小写，参数声明抹掉了语料定义，每个 `$c.Key` 都是 `null`。

## D. 单个严重缺陷

**`FSCTL_SET_REPARSE_POINT` 的访问位写错**：

```csharp
// 错误：FILE_WRITE_ACCESS → 0x0009C0A4
// 正确：FILE_ANY_ACCESS  → 0x000900A4
```

**IOCTL 的访问位是它身份的一部分，不是权限检查。** 位不对时内核视其为**从未定义过的请求**，返回 `ERROR_INVALID_FUNCTION`——**字面意思是"函数不正确"，读起来像文件系统拒绝，实际是"没有这样一个控制码"**。

**这个缺陷从项目存在起就在，一直被当成"这台机器不支持"。**

## E. "只改了一半"（4 例）

**同一个问题有多条路径或多层机制，修了其中一条就以为修完了。**

| 缺陷 | 改了什么 | 漏了什么 |
|---|---|---|
| **Mica 材质** | 移除了窗口背景的 Mica | **标题栏是 DWM 绘制的，它保留了 Mica**——顶栏随壁纸变色，框体是中性灰 |
| **菜单图标** | `WriteFlat`（平铺布局）正确调用 `IconFor` | **`WriteCascade`（级联布局，默认启用）把图标硬编码成 `quexe + ",0"`**——六项显示同一个程序图标 |
| **设置持久化** | `Load()` 与 `Save()` 都写了 | **Save 仍用反射重载**，裁剪构建下必然抛异常 |
| **粘贴后的"揭示"** | 单独验证 `SHOpenFolderAndSelectItems` 时它确实复用了窗口 | **程序真正调用时它不复用**——目标目录已开着也照样新开一个。判据是"API 单独能用"，不是"用户看到什么"（详见第十七节） |

**Mica 那一例最能说明问题**：早先移除 Mica 时我写下的注释是——

> *Mica is designed for windows that do not paint their own background.*

**这句话是对的，而我没有往下问一句**：标题栏算不算"窗口的背景"？**它算，而且是 DWM 画的，我碰不到。** 直到用户报告"顶栏是深蓝色"，才去查清楚。

**判定这几例靠的是同一个动作**：**在改动之后验证，而不是假定改动覆盖了全部。**

## F. "编译器早就说了"（3 例）

**三个缺陷在每次构建时都被报出来，都淹没在警告里。**

| 警告 | 内容 | 后果 |
|---|---|---|
| `CS0169` × 3 | `ProgressWindow` 的 `_detail`/`_headlineControl`/`_percentControl` **从不使用** | 改自绘文字时留下的残骸，字段还在、引用早没了 |
| `CA2014` | `JobJournal` 的 **`stackalloc` 在循环里** | 日志每 9 字节一分，**100 万条记录 = 9 MB 栈，而默认栈只有 1 MB** |
| `IL2026`/`IL3050` | `RobocSettings.Save` 用了 **裁剪下不可用的反射序列化** | **编译通过，第一次读到设置文件就崩** |

**这三条是在一次"清理警告"里被一起发现的**——在那之前，构建输出一直写着"3 个警告"，没有人读。

**后来 `bench/check-wiring.ps1` 把这一类变成了自动化检查**，但它的覆盖范围是"配置与参数"，不含编译器警告。**规则是：构建必须是零警告，而不是"警告数没变"**（见第七节规则 8）。

## H. "方法存在，但从来没有人调用它"（1 例）

**`RecycleBin.WriteMarker` 从第一个提交起就在，整个项目生命周期内没有被调用过一次。**

**后果**：回收一个**目录**时，目录被移动了、索引也记录了，**但那个让回收站认出它的标记文件从未写入**。于是 `Walk` 把它当成普通容器递归下去，里面的文件逐个去索引里查——**都查不到**。

**用户看到的是：提示「成功回收」之后点开回收站，程序说「回收站是空的」——而一个完整的文件夹就躺在里面，1015 MB，文件一个不少。**

**为什么难查**：

| 层面 | 状态 |
|---|---|
| 回收操作 | 返回成功 |
| 文件系统 | 目录确实在回收站里 |
| 索引 | 记录完整 |
| **列表** | **说没有** |

**没有任何一层报错。** 用户唯一能看见的症状是「回收站是空的」，**而那恰好也是一句合法的、正常状态下的输出**。

**根因不止是"忘了调用"**，还有一处设计不一致：

- `OriginalPathOf` 明确写着**索引是权威来源**，标记只是给旧数据的兜底
- 而 `Walk` 判断目录时**只查标记，从不查索引**

**两个方法对"什么是权威"的理解不同，各自都自洽，合起来就错。**

**修法与防线**：

1. `Walk` 对目录改为**先问 `OriginalPathOf`**（它会查索引），查不到才递归
2. `TryPut` 补上 `WriteMarker` 调用——**不只是给程序的兜底，也是给人看的说明**（标记文件里写着原位置、回收时间和还原方法）
3. **自检新增第 24 项**：回收一个目录，断言它**能被列出来**，且**带标记**

**还有一处没补的缺口**：`scripts/check-wiring.ps1` 能查「声明了却无人读取的属性与参数」，但**查不出「定义了却无人调用的私有方法」**。这一类目前只能靠编译器分析器（IDE0051），而它默认不在构建时运行。
## G. "注释与代码相反"（1 例）

```csharp
DrawTextW(dc, text, text.Length, ref rect,
    0x00000010 | 0x00000800 | 0x00000020); // WORDBREAK | NOPREFIX | SINGLELINE off
//                                          ↑ 0x20 就是 DT_SINGLELINE
```

**注释说"关闭"，代码在开启。** 后果是设置窗口的三段说明：文字不换行（冲出右边界）、三段按 160 像素往下排队（第二段在框外、第三段在窗口外）。

**这比没有注释更糟**——它让审阅者跳过这一行。

**同一次修复还暴露了配对的另一半**：`DT_CALCRECT` 必须只出现在测量调用里。**测量与绘制用的标志不配对，是这一族缺陷的根源。**

# 六、事后分析：`delete D:` 删掉了整个工作区

**这是本项目最严重的一次事故。**

## 经过

`delete D:` 被接受，Windows 把 `D:` 解释为**驱动器相对路径**（即进程当前目录），于是工作区被整个删除。

## 根因

**驱动器相对路径是 Windows 的一个语义陷阱**：`D:` 不是 `D:\`，而是"D 盘上的当前目录"。程序按字面接受了一个合法但语义意外的输入。

## 现在的三道防线

| 守卫 | 拦截 |
|---|---|
| `GuardDriveRelative` | 形如 `D:` 的驱动器相对路径 |
| `GuardAgainstVolumeRoot` | 卷根目录 |
| `GuardAgainstSelf` | 程序自身所在目录及其祖先 |

**外加**：删除需要 `--yes`，以及一次强制确认。

## 由此形成的设计原则

**破坏性操作绝不在不确定的输入上执行。** 宁可拒绝并要求用户说得更明确，也不要猜。

**这条原则后来救了回收站**——同名不再回收、回收站内项目拒绝再次回收，都是它的延伸。

# 七、维护规则

**这一节是硬性约定。违反它们不会编译报错。**

## 规则 1：空 `catch` 只允许出现在枚举、清理、或带兜底的读取路径

```csharp
catch (IOException) { }
catch (UnauthorizedAccessException) { }
```

**判定标准**：

| 允许 | 不允许 |
|---|---|
| 枚举时跳过不可读项 | 移动、删除、写入失败被吞掉 |
| 清理失败无害（残留文件留着） | 有数据完整性后果的失败 |
| 读取有下一级兜底（边车→标记→算术） | 唯一的记录渠道 |

**当前 78 处，已逐处核查，全部属于允许类别。** 但**新增时必须先确定属于哪一类**——把这个 catch 复制到删除路径上，编译通过、测试通过、行为是静默丢数据。

## 规则 2：新增带值参数后，必须注册进 `Args.TakesValue`

**否则它的值会被当成位置参数**，报出 `roboc: source not found: 32`——**既不提那个参数，也不提遗漏**。

```powershell
powershell -ExecutionPolicy Bypass -File scripts\check-wiring.ps1 -Root .
```

**退出码 0 = 通过。建议每次发布前跑。**

## 规则 3：新增 `CopyOptions` 属性后，必须确认有读取点

同一个检查器覆盖。**一个只被赋值、从未被读取的属性，会让读代码的人以为某个行为已经实现。**

## 规则 4：`.ps1` 必须带 UTF-8 BOM

## 规则 5：发布前必须杀残留进程，并确认完整性标签

## 规则 6：破坏性操作必须走守卫

## 规则 7：先让问题可观测，再改代码

**本项目四次"失败信息未抵达"说明：改代码之前先确保失败会说话。**

## 规则 8：构建必须是零警告

**不是"警告数没变"，是零。**

三个真缺陷在构建输出里躺了很久，写法一直是"3 个警告"——**一个不变的数字等于没有信息**。见第五节 F 类。

```powershell
dotnet build Roboc.slnx -c Release -v minimal
# 期望：0 个警告，0 个错误
```

**新增警告必须当次处理**：要么修，要么在代码里写明为什么可以忽略（而不是在构建日志里）。

## 规则 9：改动之后验证，而不是假定

**同一个问题往往有多条路径、多层机制。** 修了一条不等于修完：

- 移除了窗口背景的 Mica —— **标题栏是 DWM 画的，还在用 Mica**
- 修好了平铺布局的图标 —— **默认启用的级联布局是另一段代码**
- 写好了设置的读取 —— **保存仍用着裁剪下不可用的重载**

**验证的具体形式**：改了默认布局就测默认布局；改了窗口的一部分就看整扇窗；**改了配置的两端就两端都测。**

# 八、视觉规范

**所有界面元素的唯一依据。数值在此声明一次，代码中不得出现第二处。**

## 根本原则

```csharp
// 字体：磅 → 像素
int height = -(int)Math.Round(points * dpi / 72.0);

// 布局：按 96 DPI 声明逻辑像素
private static int Scaled(int pixels, int dpi) => pixels * dpi / 96;
```

**窗口创建前必须用 `GetDpiForSystem()`**，并用 `AdjustWindowRectExForDpi` 算上边框与标题栏。

## 纵向节奏（96 DPI 逻辑像素）

```
 20  标题行 (10pt)          20 .. 33
 46  百分比 (19pt)          46 .. 71
 86  当前文件名 (9pt)       86 .. 98
108  进度条 (8px)          108 .. 116
134  速率曲线 (92px 固定)   134 .. 226
250  详情三行 (行距 26px)   250 .. 306
────────────────────────────────────
客户区高度 320，窗口 510 × 352
```

**两条铁律**：

1. **曲线高度固定，不用"剩余空间"**——弹性高度会吸收文本带之间的舍入差
2. **改动任何一条带，必须重算整条节奏**——曾缩小卡片却未重排，导致文件名长进进度条

## 字号层级

| 用途 | 磅值 | 175% 下 |
|---|---|---|
| 进度窗标题行 | **10 pt** | 23 px ← **基准** |
| 弹窗正文 / 弹窗按钮 / 进度窗按钮 | **10 pt** | 23 px |
| 进度窗百分比 | 19 pt | 44 px |
| **进度窗详情行** | **9 pt** | 21 px ← **唯一例外**（次要读数） |

## 配色

**从系统读取，不写死。**

| 用途 | 来源 |
|---|---|
| 深浅主题 | `HKCU\...\Themes\Personalize\AppsUseLightTheme` |
| 强调色 | `HKCU\Software\Microsoft\Windows\DWM\AccentColor`（**ABGR**，需 `& 0x00FFFFFF`） |

## 网格线调参记录

| 版本 | 横向 | 纵向 | `GraphGrid` |
|---|---|---|---|
| v1 | 3 | — | `Lighten(rgb, 0.42)`——被填充覆盖，不可见 |
| v2 | 3 | — | `0.42`——修正顺序后可见，对比偏强 |
| **v3** | **3** | **9** | **`0.52`** ← 当前 |

**参照**：曲线填充 `Lighten(rgb, 0.72)`。**数值越大越浅**，要减小对比就向上调。**后续微调步长 0.05。**

## 窗口外观

```csharp
private const uint WS_CLIPCHILDREN = 0x02000000;   // 不可省
private const uint WindowStyle = WS_OVERLAPPED | WS_CAPTION | WS_SYSMENU | WS_CLIPCHILDREN;

DwmSetWindowAttribute(hwnd, 33, ref round, sizeof(int));          // 圆角

// 标题栏由 DWM 绘制，必须在窗口显示前设置
if (DwmSetWindowAttribute(hwnd, 20, ref dark, sizeof(int)) != 0)
    DwmSetWindowAttribute(hwnd, 19, ref dark, sizeof(int));       // Win10 旧编号
```

**没有 `WS_CLIPCHILDREN`，父窗口的绘制不会避开子窗口**——而进度窗每秒重绘十次整个客户区，**按钮会被创建、正确定位、然后每一帧都被涂掉**。

## 速率曲线

**两级平滑**：移动平均（窗口 3）去除瞬时尖刺 → Catmull-Rom 样条转三次贝塞尔消除折角。

**采样 120 个 × 100ms = 12 秒历史。**

**填充与描边必须共用同一条路径**：

```csharp
BeginPath(dc);
MoveToEx(dc, points[0].X, points[0].Y, 0);
PolyBezierTo(dc, curves, curves.Length);
LineTo(dc, x + width, y + height);
LineTo(dc, x, y + height);
EndPath(dc);
StrokeAndFillPath(dc);      // 画刷填充 + 画笔描边
```

**窗口尺寸必须先于布局确定**：`_dpi = ScaleFor(_window)` 在 `Layout()` 之前。

## GDI 纪律

**每个画刷、画笔、区域、位图都必须 `DeleteObject`。** 每次刷新泄漏三个，几分钟后所有绘制调用静默失败——**画面变空白而不是变错，极难定位**。

**字体对象按实例缓存、不释放**：可接受（进程退出即回收），**但若将来一个进程显示多个对话框，这里会变成真泄漏**。

# 十、性能数据与测量纪律

## 测量纪律：这台机器的存储会被自己的负载拖垮

**卷会因反复的小文件读写而劣化，只有重启能恢复。**

历史记录——**同一时刻、同一操作、仅卷不同**：

| | D: (Disk 0) | E: (Disk 1) |
|---|---|---|
| 300 × 4KB 创建 | 504 文件/秒 | 1999 文件/秒 |
| 16 MB 顺序写 + fsync | **1 MB/秒** | 289 MB/秒 |

**差 2000 倍。**

**因此：**

1. **只跑 `scripts/run-perf.ps1`，不要零散反复测**
2. **交错执行、轮转顺序、每轮前后测卷健康**
3. **漂移 >20% 的轮次整轮作废**（只标注不剔除会让污染数据照样进中位数）
4. **建议每次测试会话前重启**

**健康参照：约 3900 文件/秒。**

## 最终性能结论

| 目标 | 结论 | 证据 |
|---|---|---|
| **复制持平或略超 robocopy** | **最好成绩持平，稳定性显著更好** | Roboc 跨轮波动 7%，Robocopy/MT:32 波动 114% |
| **删除优于 PowerShell rm** | **是，健康状态下 2–3 倍** | 三轮一致，从未失败 |
| 大文件差距 | **不存在** | 见下 |

### 大文件的"3.8 倍差距"是测量假象

| 测量 | 数值 | 性质 |
|---|---|---|
| 卷的真实持续写入（`Flush(true)`） | **967 MB/s** | 物理上限 |
| 纯写入不 flush（.NET） | 4109 MB/s | 缓存吸收 |
| **Robocopy/MT:32** | **11,100 MB/s** | **缓存数字，数据尚未落盘** |
| **Roboc** | **831–1034 MB/s** | **真实落盘 = 上限的 86–107%** |

**robocopy 自报 11.1 GB/s，是该卷物理能力的 11 倍。**

**机制**：`OverlappedPipeline.cs:198` 在每个续传检查点 flush——**这是日志正确性的要求**（日志不得声称拥有断电后可能丢失的字节）。

**`--no-flush` 管不到它**（只关文件末尾那次 flush）。**已写进代码注释。**

**受控测量证明检查点间隔不是杠杆**：

```
32MB / 128MB / 512MB / no-resume  →  中位数 0.93–0.99s，极差完全重叠
```

**大文件复制就是磁盘受限，到头了。**

## 测量方法比结论更容易出错

**同一个 1 GB 间隔变体，未受控时测出 4.11s，受控（每次暖源）后测出 0.99s。**

**顺序执行的变体会互相淘汰缓存**——**后来者的数字描述的是缓存状态，不是被测参数。**

# 十四、测试卫生

**测试产物一律放 `artifacts\scratch\`，绝不建在盘根。**

## 为什么单列一节

2026-10-14，用户在 `D:\` 根目录发现了十几个测试目录。它们都是测试用例建的——`D:\roboc-restore-test`、`D:\roboc-marker-test`、`D:\roboc-open-verify` 之类——**每一个单看都无害，加起来是一片垃圾，而且长在别人的盘根上。**

**用户的原话：「你这样很不规范。」** 这是对的。

## 两条规则

**① 建在固定位置**

```
artifacts\scratch\        ← 所有临时目录、临时文件
%TEMP%\                   ← 只有 artifacts 不可写时
```

**绝不** `D:\<something>-test`。盘根是用户的，不是构建系统的。

**② 清理必须扫描确认，不能靠记忆**

这一条是真正被违反的那条。当天清理过两次，两次都报告"已删"，两次都漏了东西——**因为我是凭记忆列出自己建过哪些目录，而不是扫描磁盘找出来。**

```powershell
# 错误做法：凭记忆列
Remove-Item 'D:\roboc-recycle-test' -Recurse -Force

# 正确做法：扫描 + 逐个确认
Get-ChildItem 'D:\' -Force | Where-Object { $_.Name -like 'roboc-*' } |
    ForEach-Object { "  $($_.FullName)  $($_.LastWriteTime)" }
# 看一眼，确认每一项都是自己的，再删
```

**记忆会漏。扫描不会。**

## 判定"是不是我的"

**不要删任何自己不能解释来源的东西。** 当天扫描出的三类：

| 项 | 判定 |
|---|---|
| `roboc-*-test`、`%TEMP%\roboc-trim*` | **我的，删** |
| `Roboc-backup-20261013-115159` | **有意的安全网**，带验证记录。**留着，问用户** |
| `roboc-perf`（4.2 GB 语料） | **我的，但重建有代价**（卷性能退化，只有重启能恢复）。**移走而不是删** |

**最后那个改成了移动到 `D:\bench\roboc-perf`**——盘根干净了，语料还在，代价为零。

## 一条更早的教训，同源

同一天还有一次：改完代码后**直接跑 `restore --gui-errors` 测试自动打开**，通过了，于是报告"已修复"。

**但菜单根本不走那条路。** 菜单调的是 `recycle --gui-errors`，它内部再调 `restore --quiet`——`fromMenu` 是 false，那一段代码永远不执行。

**测试要通过真实入口，不是最方便的那个入口。** 这和"清理要扫描不能靠记忆"是同一个毛病：**用自己以为的替代实际情况。**

# 十五、救火记录：一次回收站缺陷的六个层次

**2026-10-14。用户报「坏了坏了重大bug」。此后六轮，每一轮都以为修好了，每一轮都有下一层。**

留这一节不是为了记流水账，而是因为**这六层里有五层是同一种毛病**。

## 六个层次

| 层 | 症状 | 根因 | 我是怎么找到的 |
|---|---|---|---|
| 1 | 回收后回收站点开说「空的」 | `WriteMarker` 从第一个提交起从未被调用 | **读代码** |
| 2 | 取回后不打开原路径 | 内部调用走 `--quiet`，`fromMenu` 为假 | **读代码**（错） |
| 3 | 同上 | `explorer.exe` spawn 被 shell 接管后丢弃 | **读代码 + 一次不相关的测试**（仍错） |
| 4 | 同上 | **取回清掉了索引，之后再查原路径必然失败** | **诊断日志** |
| 5 | 冲突时静默保留副本，用户不知情 | `--called-internally` 把菜单路径也压掉了 | **诊断日志** |
| 6 | 回收站根目录出现 `Roboc.回收信息.txt` | **一个标记文件被当普通文件回收，`Walk` 于是把整个回收站当成一项** | **完整生命周期日志** |

## 五层是同一种毛病

**第 2 到第 6 层，前两轮我都靠读代码下结论，两轮都错。第 4、5、6 层改用日志，一次定位。**

**这正是第 7 条规则说的（「先让问题可观测」），而我违反了它三次。**

**具体是怎么违反的：**

- 第 2 层：**直接跑 `restore --gui-errors` 测试**，通过了，报告"已修复"。**菜单根本不走那条路。**
- 第 3 层：改用 `ShellExecute` 后测试窗口数从 5 变 6，报告"已修复"。**那个测试证明的是 API 可用，不是 Roboc 会调它。**
- 第 6 层之前：三次解释"标记为什么在根目录"，三次都是推测。

**教训写成一句话：**

> **报"已修复"之前，必须有一次运行走的是用户真实走的那条路。**
> **代理指标（进程存活、窗口数变化、API 单独可用）不算验证。**

## 一个值得单列的发现

**第 6 层的根因里有一条隐藏的严重性：**

```
一个杂散文件 → Walk(binRoot) 的 HasMarker 为真
             → 「整个回收站」被当成一个被回收的目录
             → 用户点取回，搬走的是整个回收站
```

**修复前后列表显示的文字完全一样**（`236 B  D:\Temp\0\Roboc.回收信息.txt`），**只有项目实际是什么不同**。这类缺陷不会有任何报错。

**修法**：`Walk` 增加 `atRoot` 判断——**回收站根目录是容器，永远不是它的内容之一**。

## 顺带发现的第 1 层遗留

**同一批救火里还发现 `WriteMarker` 存在却从未被调用**——而 `scripts/check-wiring.ps1` 能查"声明了却无人读取的属性与参数"，**查不出"定义了却无人调用的私有方法"**。

**这一轮结束时的全项目扫描又抓出两个同类：`MeasureOne`（无人调用）和 `mergedIntoRestore`（只赋值不读取）。**

**这个检查缺口仍未补上。** 编译器有 `IDE0051` 能查，但默认不在构建时运行。**值得单独做一次。**

# 十七、"粘贴后新开窗口"：一次把死路走成结论的排查

**这一节和第十五节是同一族问题的两次实例**，区别是这一次最后没有靠日志，而是靠**先查证再动手**走出去的。记下来是因为它包含一个可以复用的判定：**什么时候该停止调参，改去查这条路本身是否成立。**

## 症状

**目标目录的窗口已经开着，粘贴进去之后又出现一个同目录的窗口。** 用户要手动关掉它。100% 复现。

**判定这个症状不能数窗口个数。** 旧窗口还在、新的多一个，**总数在"正常"和"出问题"两种情况下是一样的**。唯一可信的判据是窗口的**身份**（HWND）在调用前后是否变化。`bench/window-reuse-probe.ps1` 就是按这个写的。

## 走过的死路，以及它为什么是死的

**做法**：不用 `SHOpenFolderAndSelectItems`，自己找到显示目标目录的窗口，把选中设进去。

**第一步**：`IServiceProvider::QueryService(SID_STopLevelBrowser, IID_IShellBrowser)` 拿 `IShellBrowser`，再 `QueryActiveShellView` 拿 `IShellView`。

**结果**：

| 调用方式 | 返回值 |
|---|---|
| 手工虚表调度（不做托管编组） | `E_NOINTERFACE` |
| 托管 COM 编组 | `S_OK`，加一个 8 字节**未对齐**的指针 `0xE072C` |

**在 `0xE072C` 上调 `Marshal.Release`，连崩三次。**

**当时的结论是"我的声明写错了"。** 这个结论是错的，而它有很强的诱惑力：两个调用方式给出不同答案，看起来一定有一边写错了。

**真正的答案要查文档才有**：

1. `QueryService` 在 `servprov.h` 里声明为 **`[local]`** —— 它不是 oleautomation 方法，只能通过同进程的代理转发
2. `IShellBrowser` 自身含 `[local]` 方法（`SendControlMsg`、`SetToolbarItems`），`IShellView` 含 `[local] AddPropertySheetPages`，`IFolderView` 整个是 `[unique][object]` 非 dual
3. **含 `[local]` 成员的接口根本无法被完整封送**，所以它们设计上就是 in-process 的
4. 微软对 `IShellBrowser` 的前置条件原话是：**"Objects that have access to the site chain of the browser"**

**所以这条路对外部进程不存在。不是声明写错，是没有这条路。** 那个 `E_NOINTERFACE` 是真相，`S_OK` 加垃圾指针才是假象。

**顺带纠正一个更早的误判**：`Shell.Application` 的 `Windows()` 返回的是 **`IShellWindows` 集合，不是 `IWebBrowser2`**。集合的 `IServiceProvider` 确实回答 `S_OK` —— 那正是让这条死路看起来有希望的东西。`LocationURL`/`HWND`/`Document` 是**元素**的属性。

**托管那边为什么是 `S_OK` 加垃圾**：`[ComImport]` 接口缺 `[PreserveSig]` 时，CLR 会把返回值搬成一个**额外的 out 参数**，整组参数随之错位，`out nint` 读到一个从未被写过的栈槽。**它表现为"成功"，比崩溃更危险。**

## 可复用的判定

> **如果同一处改了几轮还在反复，那不是"快好了"，是"模型错了"。停下来，先把"为什么会反复"本身当成问题。**

**这一轮的反复形态是**：同一个 API，有人说它复用窗口、有人说它不复用，两边的实验都能重复出来。

**这里的正确动作是去问"这个 API 有没有承诺过复用"，而不是继续调参数。** 答案是：

- MSDN 对 `SHOpenFolderAndSelectItems` 的**全部**窗口相关文字只有一句 *"Opens a Windows Explorer window with specified items in a particular folder selected."*
- 它**从未承诺复用已经打开的窗口**，也**没有记录任何"什么情况下改为新开"的条件**
- `dwFlags` 只定义了 `OFASI_EDIT` 与 `OFASI_OPENDESKTOP` 两个值（`ShlObj_core.h`）
- `SHOpenFolderAndSelectItemsEx` **不存在**（整个 10.0.26100 头文件树里 `SHOpenFolderAndSelectItems` 只有一处声明，`Ex` 形式零处）

**一个没有承诺的行为，不值得为它调参。** 这就是停止点。

## 修法

**不再依赖那个 API 的复用行为，改为自己去设置选中。** 走已经验证可用的那条路：

```
Shell.Application → Windows() → 元素 → Document → IShellFolderViewDual::SelectItem
```

**只有"没有任何窗口显示目标目录"时才回退到原 API** —— 而那种情况下"开一个窗口"正是期望行为，回退不是妥协。

**两个实测出来的坑**：

| 坑 | 后果 |
|---|---|
| 用 `LocationURL` 匹配文件夹 | 地址栏字符串把**空格**转成 `%20` 而**中文不转**，天真比较在带空格的目录名上必然失败 |
| 给每一项都传 `SVSI_DESELECTOTHERS`（0x4） | 它的语义是**"取消其他所有选中"**，不是"开始新选择"。三项只有最后一项被选中，**从外面看像成功** |

**第二个坑只有多项测试才能发现。** 单项测试在这个 bug 存在时会给出"通过"。

## 这一节要留下的三件事

**一、代理指标不算验证。** 单独调用 API 成功、窗口数没变、进程没报错 —— 这些都可能在你测的那条路上成立，而在用户走的那条路上不成立。**验收标准是用户走的那条路。**

**二、区分"我写错了"和"这条路不存在"。** 前者改代码，后者改方向。**判据是文档里的前置条件**，不是自己反复试出来的成功率。试出来的成功率会被"有时能行"长期掩盖。

**三、能力可能已经在项目里了。** 第五节 E 类、第十六节第六条都记过同一件事，而这一次又验证了一遍：`ExplorerSelection` 早就在用 `Shell.Application` 枚举窗口、已经能匹配文件夹、已经在生产路径上服务"选中超过 15 项"那个问题。**缺的只是"往已有窗口里设置选中"这一步。**
