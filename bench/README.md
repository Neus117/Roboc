# bench —— 测量脚本

这个目录放的是**测量工具**，不是构建产物，也不是测试。

为什么它们必须存在，而不是"需要时手打三行命令"：手打测量代码在本项目里已经出过两次事故，两次都不是代码错，是**测量方法错**——

- 三次复制同时跑（`&` 不等待 GUI 子系统 exe），三组数据全部作废
- 数窗口个数来判断"有没有新开窗口"，而那个症状恰恰是**总数不变**

脚本把这两类错误固化成流程，手打时不会漏。

| 脚本 | 测什么 | 什么时候用 |
|---|---|---|
| `worker-sweep.ps1` | worker 数对墙钟与 `create dest` 的影响 | 怀疑磁盘争用、或要重新确认"worker 数不是杠杆"这个结论 |
| `window-reuse-probe.ps1` | `SHOpenFolderAndSelectItems` 是复用目标窗口还是新开一个 | 改动粘贴/取回的"揭示"路径之后；或回退路径是否被走到 |

## 通用纪律

**跑之前先看脚本头部的注释块。** 每个脚本的注释块里写了它为什么存在、以及它替你避免了哪个具体错误。

**占用大空间的脚本自己做收尾，但被杀掉时不会。** 比如 `worker-sweep.ps1` 每轮清空目标目录；一次被中断的运行会留下半份语料。参考 `.gitignore` 里对 `scripts/scratch/` 等的说明。

**卷会因测量而劣化，只有重启能恢复。** 见开发者文档 §10。数字明显不合理时先怀疑环境，再怀疑代码。

## window-reuse-probe.ps1 的两个特别之处

**一、判据是窗口身份（HWND），不是窗口个数。**

用户报的症状是"目标目录已经开着，粘贴后又新开一个"——那种情况下窗口**总数前后一样**，数个数会得出"正常"的假结论。脚本比较 HWND 集合。

**二、它绕过了一个本项目撞过三次的坑。**

早先试图用手写的 `IServiceProvider::QueryService` 拿 `IShellView`，手工虚表调度返回 `E_NOINTERFACE`、托管编组返回 `S_OK` 加一个 8 字节未对齐的垃圾指针 `0xE072C`，在它上面调 `Marshal.Release` 连崩三次。

现在知道那条路**在架构上就不可能成功**：`QueryService` 是 `[local]` 方法，`IShellBrowser`/`IShellView`/`IFolderView` 自身都含 `[local]` 成员，所以它们根本无法跨进程封送——微软的说法是调用方必须"access to the site chain of the browser"，而外部进程拿不到。**不是声明写错，是路不通。**

脚本走的是另一条已经被验证可用的路：`Shell.Application` 的自动化模型（`Windows()` → 元素的 `Document` → `Folder.Self.Path`）。顺便一个实测到的坑：**匹配文件夹必须用 `Folder.Self.Path`，不能用 `LocationURL`**——后者把空格转成 `%20` 而中文不转。

**三、它调用 API 会真的打开窗口**，所以脚本保证只开自己的测试窗口、并且在任何结果下都只关自己开的那些。测试文件夹至少要有一个条目，否则脚本拒绝运行（空目录里没有可选项，实验无效）。
